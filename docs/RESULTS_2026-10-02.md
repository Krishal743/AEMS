## Deployed configuration

**Stage 1** — six branches, z-scored per query over the gallery, combined with
fixed weights:

| Branch | Encoder | Weight | R@1 alone |
|---|---|---|---|
| dense | E5-base passages (400-token chunks) | 1.0 | 0.6241 |
| bm25 | lexical over passages + title/description/tags | 0.5 | 0.5499 |
| text | CLIP caption (description + transcript) | 0.25 | 0.3894 |
| visual | CLIP ViT-B/32, 16 frames mean-pooled | 0.25 | 0.1942 |
| audio | WavLM-Large → adapter → CLIP text space | 0.25 | 0.0532 |
| chunk | CLIP passages | 0.0 (dropped) | 0.3651 |

Shortlist recall@100 = 0.8658, the ceiling for stage 2.

**Stage 2** — top 100 rescored by MiniLM fine-tuned on AEMS, reading the query
against each candidate's 8 best passages (max-pooled). Final score = stage-1
score + 0.3 × z-scored reranker score.

## Two findings that contradict the project's framing

**1. Fusion is no longer adaptive, because adaptive lost.** The gating network
predicts per-query weights and is still available (`--fusion gate`), but tuned
fixed weights beat it on both splits — validation 0.7100 vs 0.7075, test 0.6873
vs 0.6865. Once a strong dense retrieval branch exists, per-query reweighting of
the others stops paying for itself. Query-dependence survives in the per-query
z-scoring and in the cross-encoder; **branch weighting is static**.

**2. The CLIP passage branch is redundant.** Leave-one-out on validation, with
the surviving weights retuned each time:

| Dropped | val R@1 | Δ | recall@100 |
|---|---|---|---|
| nothing | 0.7100 | — | 0.8734 |
| chunk | 0.7091 | −0.0009 | 0.8762 |
| visual | 0.7093 | −0.0007 | 0.8744 |
| text | 0.7079 | −0.0021 | 0.8730 |
| audio | 0.7051 | −0.0049 | 0.8699 |
| bm25 | 0.6657 | −0.0443 | 0.8646 |
| dense | 0.6608 | −0.0492 | 0.8625 |

Measured end-to-end, dropping chunk costs 0.0025 at stage 1 but gains 0.0023
after reranking (paired CI [−0.0007, +0.0051], not significant) because the
shortlist improves. It is dropped: no measured cost, one less branch. Its
embeddings are retained because the cross-encoder uses them to select passages.

**Two branches do nearly all the work.** BM25 and E5 account for −0.044 and
−0.049 when removed; visual, CLIP caption and audio together account for under a
point. This is, in substance, a text retrieval system over a multimodally
indexed corpus.

## Caveats

**1. BM25's strength is partly a benchmark artifact.** A query's content words
appear in its own transcript 4.6× more than in a random one (44% vs 9.5%): the
QA questions reuse transcript wording. On free-form user queries the lexical
branch would likely contribute less. The dense branch is less exposed to this,
but not immune — both are text-matching the same transcripts.

**2. Test was observed repeatedly.** Every selection decision used validation,
but the harness prints test metrics on each run, so test numbers were seen many
times during development. Weaker than a single sealed evaluation.

**3. Only text queries are evaluated.** All 5,097 test queries are QA questions.
The image, video, audio and mixed query paths exist in code and are **unmeasured**.
The cross-encoder cannot serve them at all (it scores text against text).

**4. The multimodal branches contribute little.** Visual +0.0007, audio +0.0049
by leave-one-out. They are cheap to keep and are the only non-text signal, but
no current measurement shows them mattering much on this benchmark.
