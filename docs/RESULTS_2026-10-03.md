## What changed since 2026-10-02

The dense retriever was the last model in the system still off the shelf. It was
fine-tuned contrastively on in-domain pairs (positive = the query's own video's
passage, negatives = passages of other fit videos plus in-batch negatives),
selecting on validation R@1 of the dense branch alone.

| Measure | Before | After |
|---|---|---|
| Dense branch alone, validation R@1 | 0.6392 | **0.6921** |
| Dense branch alone, test R@1 | 0.6241 | **0.6775** |
| Stage-1 recall@100, test | 0.8654 | **0.8862** |
| Deployed system, test R@1 | 0.7120 | **0.7310** |

The recall@100 move matters most: it is the ceiling on everything stage 2 can
do, and it had been the binding constraint since the two-stage design landed.

## Deployed configuration

**Stage 1** — six branches, z-scored per query over the gallery, fixed weights
(`bin/training/tune_fusion_weights.py`, coordinate ascent on validation):

| Branch | Encoder | Weight | R@1 alone |
|---|---|---|---|
| dense | E5-base passages, **AEMS fine-tuned**, 400-token chunks | 1.1 | 0.6775 |
| bm25 | lexical over passages + title/description/tags | 0.5 | 0.5499 |
| visual | CLIP ViT-B/32 frames, best-frame max-sim | 0.3 | 0.2688 |
| text | CLIP caption (description + transcript) | 0.2 | 0.3894 |
| chunk | CLIP passages, max-sim | 0.1 | 0.3651 |
| audio | WavLM-Large → adapter → CLIP text space | 0.1 | 0.0532 |

Shortlist recall@100 = **0.8862**, the ceiling for stage 2.

**Stage 2** — `--rerank chain`: the top 100 are rescored by the per-candidate
gate (β=0.5), then by MiniLM fine-tuned on AEMS reading the query against each
candidate's 8 best passages (α=0.5).

## On "adaptive"

Two different models are called gating here, and they behave differently:

**The global gating network is not adaptive in practice.** It predicts one
weight vector per query, but the deployed checkpoint emits the *same* vector for
every query — the evaluation harness reports `± 0.0000` standard deviation on
all six weights (visual 0.12, text 0.08, chunk 0.10, audio 0.10, bm25 0.20,
dense 0.40). It has learned a fixed weighting, and scores 0.7126 against 0.7159
for weights tuned directly. Calling this branch adaptive would be inaccurate.

**The per-candidate gate is genuinely query- and candidate-dependent**, and it
is the one deployed, inside the chain. Retrained on the six branches over seeds
42/100/200 it reaches validation R@1 **0.7352 ± 0.0007** against 0.7343 for
stage 1 alone — a **+0.0009 mean gain, at the edge of noise**. Its contribution
has shrunk as the dense branch strengthened: there is less for per-query
reweighting to recover once one branch is reliably right.

This is reported as measured rather than as a win. Adaptive fusion remains a
required part of the system and stays in the deployed path, but on this
text-query benchmark it is currently carrying very little of the score.

## A tuning result worth recording

Unconstrained coordinate ascent sets the two CLIP-text branch weights to zero
and reaches validation 0.7357, against 0.7343 when every branch is held at a
floor of 0.1. The paired bootstrap on that difference is **+0.0014 [−0.0014,
+0.0042]** — it includes zero. The six-branch configuration ships: there is no
measured gain to be had from dropping the branches, and keeping them preserves
the multimodal fusion the system is for.

This also reverses the previous round's "the CLIP passage branch is redundant"
finding, which was measured before frame-level visual landed. Branch redundancy
has now been configuration-specific twice; it should be re-measured after any
encoder change rather than treated as settled.

## Caveats

**1. BM25's strength is partly a benchmark artifact.** A query's content words
appear in its own transcript 4.6× more than in a random one (44% vs 9.5%): the
QA questions reuse transcript wording. On free-form user queries the lexical
branch would likely contribute less. The dense branch is less exposed but not
immune — and fine-tuning it on these same questions may have increased, not
decreased, its fit to this phrasing.

**2. Test was observed repeatedly.** Every selection decision used validation,
but the harness prints test metrics on each run, so test numbers were seen many
times during development. Weaker than a single sealed evaluation.

**3. Only text queries are evaluated here.** All 5,097 test queries are QA
questions. The image, video, audio and mixed query paths are now measured
separately in `docs/RESULTS_MULTIMODAL_2026-10-03.md`, but on a
query-by-example task (a clip cut from the target video, matched back to it)
that is not comparable to this one. The cross-encoder still cannot serve them
at all — it scores text against text — so stage 2 is unavailable outside text
queries.

**4. The multimodal branches contribute little.** Visual and audio together
account for well under a point by leave-one-out. They are cheap to keep and are
the only non-text signal, but no current measurement shows them mattering much
on this benchmark. This remains the honest summary: a text retrieval system over
a multimodally indexed corpus.
